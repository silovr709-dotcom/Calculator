# РЕцепт PRO — архитектура развития (предложение)

Статус: **предложение до реализации**. Масштабная переделка не начиналась.
Документ фиксирует анализ существующего калькулятора и план трёх направлений:
финансы/выручка, база знаний, бланк на фабрику.

---

## А. Что уже есть в проекте

**Стек:** Vite + React + TypeScript, расчётное ядро — чистые функции в `app/src/lib`, 147 тестов (vitest), деплой на GitHub Pages из ветки.

**Данные расчёта (где лежат):** всё локально, `localStorage` через `lib/storage.ts`
(`K_PROJECTS`, `K_TEMPLATES`, `K_SETTINGS`, `K_PRICEBOOKS`), резервные копии JSON +
экспорт/импорт (SyncPanel). Проект — единый объект `Project`: строки расчёта `lines`,
модули `modules`, настройки `settings` (наценки, расходы %/₽), `variants`, `sketch`,
`measurement`, `clientOffer`, фото, статус `draft/sent/approved/archived`, даты.

**Финансовое ядро уже считает (lib/engine.ts → `Totals`):**
стоимость для клиента (`client`), себестоимость (`cost`), наценка в ₽ и %
(`markupRub`, `markupPct`), маржинальность (`marginPct`), доп. расходы
(`extraTotal` + построчная `extraDetails`, фикс ₽ и % от суммы проекта),
суммы по группам, правило эмали, округление цены клиента.

**Калькулятор умеет:** модули с конструкцией и слотами материалов, дефолтные
материалы проекта, быстрые пресеты и готовые комплекты кухонь, опоры,
технички фасадов/петель/надбавок с рекомендациями, чек-лист обязательного
состава (столешница/стеновая/цоколь/плинтус) с подтверждением отсутствия,
варианты «Эконом/Стандарт/Премиум» (переопределение фасадов, фурнитуры,
столешницы и стеновой), эскиз по стенам, замер, мастер, клиентское КП,
экспорты XLSX/CSV/JSON, undo, массовые операции, проверка укомплектованности.

**Навигация:** верхние вкладки `View` в App.tsx: dashboard / project / quick /
pricebook / settings / sync.

## Б. Что используем повторно (не дублируем данные)

| Нужно для PRO | Уже есть |
|---|---|
| Цена клиента, себестоимость, расходы, прибыль, маржа | `calcTotals()` + расходы %/₽ |
| Проверка перед бланком | `checkModule()` (ошибки/предупреждения), чек-лист, строки без цены, устаревшие технички |
| Состав заказа для бланка | модули → `moduleToLines()` с размерами/количеством, дефолтные материалы |
| Справочники значений | прайс (`Pricebook`), пулы слотов и чек-листа |
| Документирование статуса | `Project.status` + фильтры дашборда |

## В. Чего не хватает

1. **Финансовая сводка по ПОРТФЕЛЮ проектов** (сейчас итоги есть только внутри проекта).
2. **База знаний** — раздела нет вообще.
3. **Бланк на фабрику** — нет ни данных спецификации, ни модуля. **Бланк и инструкция

   справочники и зависимости определять нельзя (не придумываем).

## Г. Как организовать РЕцепт PRO

Верхний уровень (один экран-оболочка, текущий виноградно-стеклянный стиль):

**РЕцепт PRO** — 📊 Проекты/выручка · 🧮 Калькулятор · 📋 Бланк на фабрику · 📚 База знаний · ⚙️ Настройки (+ существующие Прайс / Быстрый расчёт / Синхронизация).

Расширение `View`: `{ kind: 'factory' }`, `{ kind: 'knowledge' }`. Ничего существующее не переименовываем и не удаляем.

### 1. Финансы
- `lib/finance.ts`: `projectFinance(project, pricebook)` — тонкая обёртка над
  `calcTotals`, отдаёт `{ clientPrice, cost, extrasTotal, grossProfit, marginPct, status, unpricedCount }`.
- Дашборд: сводная строка по текущему фильтру (выручка, себестоимость, доп. расходы,
  валовая прибыль, средняя маржа) + в карточке проекта: цена клиента, прибыль, маржа, статус.
- Всё считается из существующих данных — новых правил не вводим.
- Расширяемо: позже сюда же этапы оплат/себестоимость работ — отдельным блоком, не ломая.

### 2. База знаний
- Модель данных (`types.ts`): `KbArticle { id, title, category: KbCategory, tags: string[], body: string (markdown), updatedAt }`, категории фиксированным списком:
  инструкции, правила расчёта, фабрики, материалы, фасады, фурнитура,
  технические требования, оформление заказов, внутренние регламенты, ЧаВо.
- Каждая статья — самостоятельный документ с метаданными → позже прямо ложится в
  AI-поиск (статья = чанк; теги/категория = фильтры). AI-слой сейчас НЕ делаем.
- Хранение: `K_KNOWLEDGE` в `storage.ts` (входит в резервную копию), без нового бэкенда.
- UI `KnowledgePanel`: слева категории, сверху живой поиск по заголовку/тегам/тексту,
  карточка статьи, простое создание/редактирование статей (внутренние пользователи сами ведут базу).
- Контент не придумываем: структура пустая + 2 статьи-ссылки на существующие `docs/` (правило эмали, техничка фасадов).

### 3. Бланк на фабрику
Архитектура «Фабрика → тип бланка → правила → шаблон», чтобы добавлять фабрики
без переписывания:

```
lib/factoryBlank.ts
  interface FactoryBlankField { key; label; required: boolean;
    source: 'project' | 'manual' | 'dict';     // откуда значение
    dictRef?: string;                          // справочник (напр. «цвет фасада»)
    dependsOn?: { fieldKey, values } ;         // зависимости между полями
    validate?: (value, ctx) => string | null;  // проверки из инструкции
  }
  interface FactoryBlankSpec { factoryId; blankType; version; fields: FactoryBlankField[]; crossChecks: [] }
  draftFactoryBlank(project, pricebook, spec) → { values, missing, check }
```

- `draftFactoryBlank` автоматически подставляет из проекта то, что уже введено
  (фасад/материал/размеры/количество/фурнитура/столешница — по правилам бланка),
  ручного повторного ввода нет.
- В проекте хранится черновик: `Project.factoryBlankDraft?: { specId, values, updatedAt }` (optional → совместимость).
- Конвейер: **Калькулятор → проверка → черновик бланка → проверка по правилам фабрики → печать/экспорт**.
- Правила и поля — только из предоставленного бланка и инструкции после их изучения.

## Д. Как будет работать формирование бланка

1. В проекте нажимаем «📋 Бланк на фабрику» (или раздел выбирает активный проект).
2. Система: блок «Готовность проекта» (см. Е) → собирает черновик из данных проекта →
   показывает поля бланка по секциям: ✅ заполнено из проекта / 🟡 не хватает (ввести вручную или выбрать из справочника) / 🔴 ошибка правила.
3. Ручные поля сохраняются в черновик проекта (не дублируются в других местах).
4. Когда ошибок нет — «Сформировать документ» (печатная форма/файл по шаблону бланка).
5. Ничего молча не исправляем: ошибки показываются понятным текстом, пользователь правит.

## Е. Проверки перед формированием

Уже существующие (переиспользуем):
- модули без обязательных данных (`checkModule` errors: размеры, корпус, петли/ручки/опоры без модели);
- неподтверждённые предупреждения (молчаливые расхождения);
- чек-лист обязательного состава (столешница/стеновая/цоколь/плинтус или подтверждение отсутствия);
- строки без цены (`unpricedCount`), устаревшие технички фасадов/петель.

Новые — строго из инструкции по бланку (обязательность полей, справочники,
зависимости, форматы). Список составим после изучения документов, пример формата сообщений:
🔴 «Не заполнено поле “Тип фасада”» · 🟡 «Для выбранного элемента отсутствует обязательная фурнитура».
